# UI Requirements (Phoenix + LiveView)

## Stack

- Phoenix 1.7 + LiveView 1.0, Bandit server.
- Tailwind CSS + `@tailwindcss/forms`, esbuild, heroicons (via the mask plugin).
- HTTP client to the REST API built on `Req`/`Finch`.
- No Ecto — the UI has no database of its own; all data comes from the API.

## Internal modules (our code)

| Module | Responsibility |
|--------|----------------|
| `Api.HttpClient` | Wrapper over `Req`: `get/post/put/delete/patch_json`, base URL from config, bearer token, body normalization, timeouts/retries. |
| `Api.ResultParser` | Parse the `{success, data}` envelope from the API and extract error details (`detail`/`message`); extract the token from the login response. |
| `Api.*` (resource) | One module per resource: Auth, Teams, Epics, Tickets, Comments — thin functions over `HttpClient`. |
| `auth.ex` | Session: plug `fetch_current_user`, `require_authenticated_user`, `on_mount :ensure_authenticated` for `live_session`, token in a cookie, logout. |
| `components/core_components.ex` | Shared components: flash, icons, buttons, forms, modals. |
| `components/layouts` | root + app layout (header with a user menu and Log out). |

## Screens (minimum)

| Screen | Type | Notes |
|--------|------|-------|
| Create profile | dead view (controller + heex) | email, displayName, password + confirmation |
| Login | dead view | email + password |
| Kanban board | LiveView | primary screen, team selector |
| Ticket: create / edit / details | LiveView modal over the board | all fields + comments |
| Team management | LiveView | delete disabled for non-empty teams |
| Epic management | LiveView | delete disabled for referenced epics; team fixed after creation |

## Kanban board (primary screen)

- Exactly **5 columns** in workflow order: `new` → `ready_for_implementation` → `in_progress` → `ready_for_acceptance` → `done`. Canonical API values are shown as human-readable labels with spaces.
- A card shows at least **title and type**; the epic is recommended.
- Within-column sorting: `modified_at DESC` (most recently modified first). Manual ordering is not persisted.
- Entry points: create a ticket and open an existing one.
- Filters: by **type**, by **epic**, plus a case-insensitive substring search over **title**. Combined with AND; performed server-side via API query parameters.
- The board remains usable with **100+ tickets** on a single team.

## Drag & Drop

- Implementation: JS hook (SortableJS) + `pushEvent` into LiveView.
- Dropping a card into another column → optimistic move in the UI → `PATCH /tickets/{id}/state`.
- On success — the state is saved on the server (correct after refresh).
- On **error** — the card returns to its previous column **and** an error message is shown.
- Moves are allowed between any columns (sequential transitions are not required).

## Behavioral rules

- No access to the application until a successful login (guard on business routes).
- Form validation: password ≥ 8 and matching the confirmation; non-empty (after trim) team/epic/ticket names.
- When a ticket's team changes — clear/replace the selected epic (the epic list is scoped to the selected team).
- Delete buttons are **disabled** for teams with tickets/epics and for epics referenced by tickets; on a 409 from the API — show a clear message.
- Deleting a ticket — only after explicit confirmation.
- **loading / empty / success / error** states everywhere applicable.

## Data and storage

- All CRUD — only through the REST API. Browser localStorage is not used as the system of record (allowed only for UI state such as the active filter).
- The auth token is stored in a server-side session cookie, not in the URL and not in localStorage.

## Tests

At least one UI/API flow. To isolate from the backend during tests, the API is mocked (e.g., `Bypass`).
